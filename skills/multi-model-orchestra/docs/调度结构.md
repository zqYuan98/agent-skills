# 调度结构

## 一句话
最强的几个模型各自偏科，没有「版本答案」。未来用它们干最多的活，是个**管理学问题**：在合适的任务上，用合适的人。所以组合用，并且让其中一个站在中间当总指挥。

## 1 三个人的性格 → 岗位
| | Gemini | Claude | GPT（Codex） |
|---|---|---|---|
| 沟通 | **极舒服**，给情绪价值 | 还不错，主动，有时凌驾于你之上 | **没法沟通**：汇报信息密度最高但几乎没法读 |
| 审美 | 不错（略逊 Claude） | **极佳**：前端、视觉、动效 | 差 |
| 干活 | 灵性、点子最多；**粗心，幻觉最强** | 一般严谨：改不全、漏细节、没看到结果就说做完 | **极其严谨**；太听话，你写错一个事实它照着错的执行 |
| Harness | 差（但更新很勤） | **无敌**（Claude Code） | 还不错 |
| 可用性 | 随便用 | 可能不给你用 | 随便用 |
| 岗位 | **军师**：独立第二方案、文案/交互顾问 | **总指挥**：听懂·拆解·前端·验收·汇报 | **工兵＋守门人**：后端/算法/数据/性能、浏览器操控、合并前审查 |

## 2 结构
```
用户 ── 说需求 ──▶ Claude（总指挥）── 人话汇报 ──▶ 用户 ── 拍板
                      │
         ┌────────────┼────────────────────┐
         ▼            ▼                    ▼
      自己做       Gemini（军师）        Codex（GPT）
   前端/视觉/动效   · 独立第二方案       · 工兵：后端/算法/数据/性能、浏览器操控
   小改动/拆解/验收 · 文案与交互顾问     · 守门：合并前审查
                   （只读）             （沙箱 workspace-write、无网络、不许提交）
   所有外部产出都由 Claude 核实后才采信：Gemini 的判断拿代码对；Codex 的活读 diff、自己跑测试
```
用户在图里只出现两次：**说需求**，和**拍板**。

## 3 全链路
1. **理解需求、规划**。小需求总指挥直接干；大方案（架构、数据怎么存、是否长期绑定某服务、系统下一步整体怎么改）→ 自己一份＋Gemini 独立一份 → 核实合并 → 用户拍板。〔skill `dual-plan`〕
2. **前端设计**：总指挥自己做；界面文案与交互自己先做一版，再请 Gemini 当顾问改，核实后采纳。〔skill `copy-advisor`〕
3. **后端实现**：接口已定死、和页面无关的独立模块（成块的后端、算法、数据处理、性能）派给 Codex；小活自己做。〔skill `codex-delegate`〕
4. **收口**：Codex 交回后总指挥读 diff、自己跑测试、整体合并。
5. **审查**：每个合并请求上线前过 GPT 审查（两级、最多两轮、超限交用户）。没过不进 CI。〔skill `review-gate`〕
6. **沉淀**：用户纠正一次、审查退回一条，就在同一个 PR 里把这一类拦住。〔skill `error-to-check`〕
7. **汇报**：用用户听得懂的话，三句话讲清。

## 4 为什么总指挥是 Claude
站在中间的位置对人的要求最高、最全面：
- **对上**：听懂乱七八糟、只说了一半的需求。
- **对下**：把需求翻译成 GPT 能精确执行的任务；读懂并验收 GPT 交回来的一大坨；在 Gemini 自信满满的建议里分清哪些是真知灼见、哪些是它粗心看错。
- 所以必须同时满足三条：**可沟通性够好 / 智力和主动性够强 / 足够严谨**，最好能自己把工作一路推到底；还要靠 Harness 去查代码、跑命令、调工具、叫别的模型、验收。

为什么不是别人：Gemini 最好聊，但最粗心、Harness 最差——像让一个特别会说、点子特别多的同事当项目负责人，会上很爽、落地未必最高分；GPT 最严谨，但跟它说话太累。
**替身规则**：没有 Claude，可以用 Gemini 4 Neon 平替总指挥（效果会差一点，差距不大）。**反过来，顾问不可用时不要悄悄换人**（`agy-ask` 退出码 5）：明说，让用户选「跳过 / Codex 出第二份 / Claude 新上下文子代理」。

## 6 设计原则（都来自原文，也是这套东西自己遵守的）
- **独立性**：要第二意见，就只给原话和必要背景，不给自己的草稿和倾向；自己的方案落笔之前不读对方的。两份独立方案几乎每次都互补。
- **核实后采纳**：外部模型的每条判断都由总指挥拿代码/命令输出去对；没有依据的一律「不确定」。
- **沟通成本**：派一次活要写任务、读 diff、复跑测试；活小于这个成本就自己做。
- **能检查就别靠文字**：机械能判断的写成检查；能改结构让错写不出来的改结构；都不行才写文字规则。已有违规记欠账只许减少。
- **可沟通性**：人类的注意力最贵。汇报先结论、三句话讲清；外部模型的长报告留在运行记录里。

## 7 传输层：同一套角色，两种派发方式
| 角色 | CLI 脚本（**默认**，边界是硬的） | T3 Code `delegate_task`（有可见子线程、可取消；边界弱） |
|---|---|---|
| Gemini 顾问 | `agy-ask [--copy] <目录> -`：`--mode plan` ＋ `--sandbox` ＋ 事后指纹校验 | `role:research/design`，`target: antigravity / GEMINI_T3_MODEL`，`interactionMode:plan` |
| Codex 干活 | `codex-worker <工作树> -`：workspace-write、无网络、approval=never、检测违规提交 | `role:implementation`，`isolation:worktree`，`target: codex / gpt-6.2-astra {reasoningEffort:xhigh}` |
| Codex 审查 | `codex-review run`（只读沙箱、结构化输出、记账） | `codex-review prompt`（出提示词＋请求ID）→ `delegate_task(role:review)` → `codex-review record <文件> --request <请求ID>` |

差别要清楚：T3 的 `runtimeMode` 是**审批粒度**，不是「只读/不联网/不许提交」；也没有只读模式。所以 T3 路径靠 plan 模式、worktree 隔离和事后核对（`git status` / `git log`）补，**需要硬边界就用 CLI 脚本**。
两条路径用同一份提示词：`--print-prompt`（`agy-ask`、`codex-worker`）和 `codex-review prompt` 会输出「预设规范＋脱敏后的任务」。T3 里后台命令用 `t3_background_wait` 等结果。

## 8 已知限制与待你确认
1. **Gemini：T3 通道已验证，命令行 `agy` 被服务端拒绝。** T3 的 Antigravity 提供方（`gemini-4-neon`、`thought_level:high`、`interactionMode:plan`）账号验证后能用：连通性自检返回预期内容，要求它写文件时它自己拒绝，事后目录指纹不变——这是一次观察到的现象，不是隔离保证（T3 没有只读/沙箱的硬隔离，靠 plan 模式＋事后核对）。命令行 `agy`：本机被服务端的资格校验拒绝（账号/地区层面，**没有做任何绕过**），所以 `agy-ask` 只用桩验证了逻辑，`--smoke` 在这台机器上跑不通；另外本机 `agy models` 里没有 `gemini-4-neon`，只有 `gemini-4-hydrogen-*`、`gemini-3.8-flash-*`。**结论：这台机器上 Gemini 一律走 T3 路径**；哪天命令行能用了（换机器/账号），再跑 `bash .orchestra/bin/agy-ask --doctor`、`--smoke`，并按提示改 `GEMINI_MODEL`。
2. **`--agent`** 原文没解释，见 `docs/原文提示词存档.md` C。
3. **审查门只做了本地硬门**（git pre-push 转发桩，按目标 ref 判断，`--no-verify` 只有用户本人能用；绝不覆盖用户自己的 pre-push；桩在 linked worktree 里回退到主工作区的套件，哪里都找不到门脚本就拦住）。基线认不出、或「基线是猜的而被推送的提交相对它没有改动」时，门会**拦住**而不是放行（设 `git config orchestra.base <分支>`；`install.sh --git-hook` 在能确定时会替你配好）；配置里的裸分支名在 origin 有远端副本时用 `origin/<分支>`。**CI 可核验**：通过/放行时自动写审查凭证（git notes，挂在树上、不带时间戳、身份中性、不带用户原话），`codex-review publish` 发布，CI 里 `review-gate-check --ci` 核验（见 `docs/CI接入.md`）。**CI 必须用目标分支上的可信副本去跑脚本**——直接跑 PR 里的那份，PR 能把它改成永远放行。凭证是流程证据而非防篡改证明，且要让 CI 任务真的拦住合并，得在托管平台上把它设为必需的状态检查、并给 `.orchestra/**` 和 CI 配置设 CODEOWNERS——这些只能你做，示例配置没有在真实 CI 平台上跑过。
4. **外发边界**：Gemini/Codex 会读到你给它的目录和工作树。涉密仓库先问用户；脱敏只覆盖 brief/任务书/diff 里的高置信度模式（邮箱、IPv4、常见密钥格式、带引号或不带引号的「名字=值」含 JSON 字段、本机用户目录），**不覆盖 IPv6**（`a::b` 这类标识符会被误伤），不是保证。第三方日志/事件流落盘前擦掉 ISO 时间、纯日期、`HH:MM:SS` 日志前缀、JSON 里的 `ts`/`timestamp`/`created_at` 等 epoch 字段；模型自己的回答和代码不擦。
5. **守卫钩子**是 shell 解析＋字符串分析：已覆盖引号/heredoc/命令替换/`bash -c`/`eval`/保留字/包装器（env、sudo、timeout、xargs、command…）/重定向（含紧贴写法、连续重定向）/git 全局选项/`find -exec`，`command -v` 这类查询不算执行。它的解析用**差分测试**（`tests/guard-diff.mjs`，`GUARDDIFF=full` 再加 600 条组合）对着真 bash 校验——生成上千种写法，「真 bash 是否真的执行了危险调用」与「守卫拦不拦」逐条一致。挡的是「顺手/误操作」，不防有意的深度绕过（`npx codex exec`、脚本里间接调用、变量拼出命令名）。守卫自己出错时降级为「请用户确认」，不静默放行。
6. **只读校验是检测，不是隔离**：`agy-ask` 跑完比对仓库指纹（HEAD 与所有 ref；已跟踪/未跟踪文件比内容；被 `.gitignore` 忽略的 ≤1MB 文件也比内容，更大的比路径+大小+修改时间；排除 node_modules/构建产物/缓存/`*.log`，可用 `ORCH_FP_EXCLUDE` 调）。它依赖 GNU 的 find/xargs/stat/sed，缺了会静默失效——所以 `agy-ask --doctor` 会现场自检（改被忽略文件、提交新文件，指纹都必须变）。真正的只读靠 agy 的 `--mode plan` ＋ `--sandbox`（未验证，见 1）。
7. **Codex 沙箱**：本机实测 `workspace-write` 有效（写工作树外被系统拒绝）。换机器/版本请跑 `tests/smoke-live.sh`。
8. **审查凭证 / CI 核验 / 飞书通知这批改动，独立复审了 2 轮，下面这些没修、记成已知限制**（都在「诚实失误、不是恶意对手」的威胁模型之外，或要多件事凑巧才触发；要不要再审一轮、要不要修，由你定）：
   - 本机门和 `pre-push`：有人**故意**建一个和基线同名的标签（如 `origin/main`）指向未审提交，门会把标签当基线放行。能建标签的人本来就能 `--no-verify`；CI 那条路径已经堵上了。
   - 凭证写入的锁：持锁进程崩溃后留下的死锁，被两个等待者**同时**回收时，理论上两个都会进临界区，后果是丢一条凭证；`publish` 会按本机的通过记录补回。
   - `publish` 判断「凭证在不在」时，没核对 note 挂的是不是 key 里写的那棵树；凭证 ref 是空的、或远端在后继提交里把凭证删了，可能报成功而 CI 找不到——重跑 `publish`（按本机记录补）或看 CI 结果就会发现。
   - GitHub 示例（`pull_request_target`）的检查结果是否挂在 PR 头提交上、能否真的挡住合并：没验证，`docs/CI接入.md` 写了上线前的自测办法。
   这一轮另外修了：取凭证不再冲掉本机还没发布的凭证（也不顺带取标签）、`publish` 的 push 不再把调用者身份和时间写进 reflog、飞书标题同样脱敏且 URL 不被当通配展开、CI 里不认 `ORCH_GATE=off`、CI 日志里凭证字段只放安全字符。
