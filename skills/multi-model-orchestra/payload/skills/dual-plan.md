# 大方案：两份独立方案 → 核实 → 合并 → 用户拍板

**为什么**：Gemini 的思考维度和你不一样，两份独立方案放一起，几乎每次都有对方没想到的地方，很互补。但它粗心、幻觉最多——所以它的每一条判断都要你核实后才采信。

**先判断要不要用**：只有大方案才用。小事自己想清楚就做。

## 步骤

1. **写 brief（独立性全靠这一步）。** 只给两样：用户的原话（原样，别改写）＋ 必要背景（只写事实：现状、约束、已经定了的事）。
   **不给**：你的草稿、你的倾向、「是不是应该 X」这类自带答案的问法、其他模型的意见。
   **去掉**：用户姓名/邮箱/账号、本机用户目录、密钥、内网地址、时区/位置/当前时间。
2. **派 Gemini，放后台**（Bash 的 `run_in_background`）：
   ```bash
   bash .orchestra/bin/agy-ask . - <<'BRIEF'
   ## 用户原话（原样）
   """
   <粘贴>
   """

   ## 必要背景（只写事实）
   - 现状：…
   - 约束：…
   - 已经定了的事：…

   ## 要你交付
   针对上面的需求，给出你的独立方案。
   BRIEF
   ```
   第一个参数是它可以只读查看的目录（仓库根或相关子目录）。
3. **不等它。** 自己独立出方案并先写下来——**在自己的方案落笔之前不要读 Gemini 的输出**，否则就不独立了。
4. **逐条核实。** 读 Gemini 方案，每条关于代码库/现状的判断，对照代码或命令输出判对/错/不确定，依据写到「文件:行」。没有依据的论断一律按「不确定」处理，不采信。
   | # | Gemini 的判断 | 核实（对/错/不确定） | 依据 | 采纳？ |
   |---|---|---|---|---|
5. **合并**，给用户一份最终方案：**结论 → 方案 → 两份的差异与取舍 → 需要用户拍板的事（≤3 个，各附你的推荐）**。
6. 用户拍板后才开工。

## 异常
- `agy-ask` 退出码 **5**（Gemini 不可用）：明说，**别悄悄换人**。让用户选：跳过（只用你自己的方案）/ 让 Codex 出第二份 / 用 Claude 新上下文子代理出第二份。
- 退出码 **3**（只读被破坏）：先 `git status` / `git diff` 看它动了什么，向用户报告，这次的输出别采信。
- 第一次用或换了账号/模型：先 `bash .orchestra/bin/agy-ask --doctor`，再 `--smoke`。
- T3 路径的 Antigravity 若返回 **`Verification Required`**：这是账号需要在 Antigravity 里完成验证（本机已验证通过过一次，再出现就是又失效了）——和「Gemini 不可用」同样处理（明说、别悄悄换人），并告诉用户去验证账号。
- 命令行 `agy` 若返回 **`Eligibility check failed … not available in your location`**：这是服务端的账号/地区限制，**不要想办法绕**——明说，改走下面的 T3 路径。本机就是这种情况，所以这台机器上默认走 T3。

## T3 路径（没有 shell 脚本时；隔离弱于脚本）
`bash .orchestra/bin/agy-ask --print-prompt . -` 会输出「预设规范＋脱敏后的任务」的完整提示词，然后：
```
delegate_task({ role:"research", mode:"async", interactionMode:"plan",
  target:{ providerInstanceId:"antigravity", model:"<GEMINI_T3_MODEL>", options:{ thought_level:"high" } },
  task:"<上面的提示词>" })
```
T3 没有只读模式：靠 plan 模式＋事后 `git status` 核对；仓库是 git 时可加 `isolation:"worktree"`（代价：看不到未提交的改动）。型号取 `.orchestra/orchestra.conf` 的 `GEMINI_T3_*`。
