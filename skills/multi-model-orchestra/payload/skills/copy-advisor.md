# 界面文案与交互：自己先做一版 → Gemini 顾问改 → 核实后采纳

**为什么**：Claude 和 GPT 写文案有同一个毛病——不写人话，还喜欢写一大堆解释性的字。Gemini 在这块明显更好，所以让它当顾问。但它遇到专业性文案会犯病：瞎编功能、瞎给承诺——所以采纳前必须核实。

## 步骤

1. **自己先做一版**，并按这四条自查（Claude/GPT 的通病）：
   - 一句话只讲一件事；动词开头；
   - 用使用者的词，不用系统内部的词；
   - 能删的解释就删——使用者要的是「现在我能做什么」，不是「它怎么工作」；
   - 空状态、报错、按钮、提示各按各的用途写。

   反例（别这么写）：「选中对话里的一段话，点「侧边问」，就能在这儿顺便问一句，不打断它正在做的事。」
   ——把功能原理塞进一个绕口长句，使用者要先读懂机制才知道该做什么。示意改法：「想追问某段话？选中它，点「侧边问」。」
2. **写给顾问的 brief**，四样（前三样是文章要求的，第四样是为了核实而加的）：
   ```bash
   bash .orchestra/bin/agy-ask --copy . - <<'BRIEF'
   ## 这一页是给谁用的
   <使用者是谁、处在什么情境>

   ## 要让人做成什么
   <一件事>

   ## 现在的文案和交互
   文案（逐处）：
   - <位置>：<原文>
   交互：<步骤、入口、状态>

   ## 这一页实际的功能（事实，供核对，别超出）
   - …
   BRIEF
   ```
3. **核实后采纳。** 逐条对照功能实际怎么用：
   - 它写的功能真的存在吗？有没有悄悄加了承诺（速度、准确率、合规、价格、时限）？
   - 它标了「需核实」的，你去核，不要原样放进去。
   - 核实通过的大部分直接采纳；瞎编或超出功能的拒绝，并在汇报里写一句为什么。
4. **汇报**：采纳了几条、拒了几条（各一句理由），不贴整份对照表。

## 不要用
只改几个字的；纯内部工具、没有真实使用者的页面；用户已经给了定稿文案的。

## 异常
- 退出码 **5**（Gemini 不可用）：明说，别悄悄换人；让用户选「跳过 / 你自己按四条自查再多打磨一轮 / 让 Codex 提意见（它写文案不强）」。
- 退出码 **3**：只读被破坏，先 `git status` 看它动了什么。

## T3 路径
`bash .orchestra/bin/agy-ask --copy --print-prompt . -` 取完整提示词，然后 `delegate_task({ role:"design", mode:"async", interactionMode:"plan", target:{ providerInstanceId:"antigravity", model:"<GEMINI_T3_MODEL>", options:{ thought_level:"high" } }, task:"<提示词>" })`。事后 `git status` 核对没被改动。
